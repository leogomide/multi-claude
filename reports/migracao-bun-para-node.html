Migração do runtime: Bun → Node.js

multi-claude v1.0.39 · análise de impacto · 10/09/2026

Resumo: dá para fazer, e o esforço é baixo a médio. O código já usa quase só APIs node:*; o que depende de verdade do Bun é pouco e bem localizado. A maior mudança não é de código, e sim de empacotamento: o Node não executa .tsx nem remove tipos de arquivos dentro de node_modules, então o projeto passa a precisar de um build step e publicar JS compilado.

Instalações existentes: config, credenciais encriptadas e keystore continuam compatíveis, sem migração. O risco real está no fluxo de auto-update e em usuários que têm só o Bun instalado, sem o Node (veja a seção 3).

2. O que precisa ser refeito

  1. Build step (principal mudança). Hoje o pacote publica .ts/.tsx cru e o Bun executa direto. Com Node:
    • Adicionar tsup/esbuild para gerar dist/cli.js e dist/tui-process.js (ESM, jsx: react-jsx). Precisam ser dois entrypoints, porque a TUI roda em processo separado.
    • Imports com extensão .ts/.tsx (~100 ocorrências) continuam valendo se o bundler resolver; com tsc puro seria preciso rewriteRelativeImportExtensions.
    • Copiar statusline-script.mjs para o dist e revisar caminhos relativos: changelog.ts faz join(__dirname, "..", "CHANGELOG.md").
    • package.json: bin → dist/cli.js, files → dist/, engines.node ≥ 20, scripts build/prepublishOnly.
    • prepare hoje é bun link. Precisa virar build, senão a instalação via github:…#latest (que não passa pelo npm registry) instala sem dist.
  2. Spawn do claude no Windows (runner.ts, cli.ts): where claude pode devolver claude.cmd (instalação via npm). Desde a CVE-2024-27980, o Node recusa spawn de .cmd/.bat sem shell: true (erro EINVAL), coisa que o Bun tolera. Testar os dois cenários (instalador nativo .exe e npm .cmd).
  3. tsconfig: trocar @types/bun por @types/node. module: Preserve/bundler pode ficar se o bundle for feito com tsup.
  4. Testes: portar 2 arquivos para Vitest.
  5. Textos e docs: mensagens de update em i18n/locales/* (3 idiomas) e em cli.ts:287, badges e instruções em README.md/README.en.md, CLAUDE.md e processo de release.

Já compatível, sem mudanças: criptografia (node:crypto, AES-256-GCM/PBKDF2), fetch, crypto.randomUUID global, child_process, fs, Ink/React, zod, rosetta, dotenv.

4. Recomendação

  1. Fazer build com tsup para JS ESM sem APIs do Bun. Assim o mesmo artefato roda em Node ≥ 20 e em Bun, e ninguém é forçado a trocar de runtime.
  2. Tratar os dois itens de alto risco antes de publicar: a remoção do bun:ffi e um auto-update que detecta o gerenciador de pacotes.
  3. Soltar uma versão de transição (ex.: v1.1.0) com nota no CHANGELOG ("requer Node ≥ 20 ou Bun") e instruções npm i -g como padrão no README.
  4. Validar manualmente no Windows (spawn de .cmd, redimensionamento da TUI), macOS e Linux, com npm i -g, bun i -g e npx.
